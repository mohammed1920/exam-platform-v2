# تدقيق المراجع الديناميكية — 2026-10-28

## النطاق والمنهج

تمت مراجعة ملفات JavaScript الأساسية وملفات بناء GitHub Pages وواجهات API عبر محتوى المستودع على `main`. هذا تدقيق ساكن محدود؛ لم يتم تشغيل المتصفح أو Firebase أو Vercel endpoints، ولم تُنفّذ اختبارات محلية على نسخة مستنسخة. لذلك لا يُعد إثباتًا لاكتمال كل المراجع الديناميكية.

## نتائج مؤكدة من الشيفرة

### 1. تحميل وحدات الأقسام عند الحاجة

ملف `home.js` ينشئ عناصر `script` ويحمل وحدات عند فتح الأقسام:

- `mizan-pulpit.js?v=1.9`
- `laws.js?v=1.6`
- `lawyer-directory.js?v=1.2`
- `petitions.js?v=1.8`

كما يحمّل Firebase Storage Compat من مصدر خارجي عند مسار دليل المحامين. يجب إبقاء هذه الملفات في المسارات الحالية أو تحديث جميع نقاط التحميل معًا واختبار فتح الأقسام بعد ذلك. وجودها في قائمة `script src` داخل `index.html` وحدها لا يكفي؛ بعض المراجع تُنشأ وقت التشغيل.

### 2. البحث العام وبيانات الأقسام

`global-search.js` يقرأ ملفات JSON وفق المسارات:

- `data/laws/laws.json`
- `data/lawyers/lawyers.json`
- `data/procedures/procedures.json`
- `data/petitions/petitions.json`

كما يختار بادئة المسار وفق ما إذا كان عنوان الصفحة يتضمن `/exam-platform-v2`. نقل هذه الملفات أو تغيير قاعدة المسار قد يكسر البحث في المعاينة أو الموقع المنشور حتى لو بقيت الملفات صالحة.

### 3. واجهات API وروابط المقالات

- `app.js` يستدعي `/api/search-questions` ويقرأ معامل `article` من عنوان الصفحة.
- `mizan-pulpit.js` يستدعي `/api/article?id=...` ويبني رابط المقال بصيغة `/?article=...` على النطاق الجذري.
- `vercel.json` يوجّه `/sitemap.xml` إلى `/api/sitemap` و`/pulpit/:id` إلى `/api/article?id=:id`.
- مجلد `api/` مستثنى من حزمة GitHub Pages بحسب `scripts/build-pages-bundle.sh`. لذلك لا يجوز افتراض أن مسارات API نفسها تعمل على معاينة Pages؛ يجب الحفاظ على التمييز بين بيئة Vercel وبيئة Pages.

### 4. الواجهة العامة ولوحة الإدارة

`firebase-admin-panel.js` يحمّل `lawyer-admin.css?v=1.20` ديناميكيًا. كما أن `mizan-pulpit-admin.js` يضيف واجهات الإدارة إلى عناصر DOM الموجودة. النقل أو تغيير ترتيب التحميل قد يؤدي إلى فشل صامت إذا لم تكن نقاط الإدراج جاهزة.

### 5. ملفات البناء والتحقق

- `.github/workflows/update.yml` يشغّل `update_questions.py` ثم فحوصات النشر ويبني حزمة Pages.
- `validate_project.py` يفحص بنية بيانات الأسئلة، بما فيها وجود معرفات `id/uid` وصحة فهرس الإجابة.
- `scripts/validate-static-project.mjs` يفحص JSON ومراجع الأصول المحلية الثابتة؛ لا يستطيع إثبات صحة التعبيرات الديناميكية التي تُنشئها الشيفرة أثناء التشغيل.
- أضيف فحص `node --check` إلى سير النشر للتحقق من صياغة ملفات JavaScript/MJS قبل بناء الحزمة.

## قرار النقل

لا يوجد نقل تشغيلي معتمد بعد. أول مجموعة مرشحة للنقل يجب أن تكون ملفًا لا تُنشأ مساراته ديناميكيًا، ولا يعتمد على ترتيب السكربتات أو globals، وتنجح بعد نقله جميع فحوصات JSON/الأصول/الصياغة والبناء واختبار المتصفح. الملفات المذكورة أعلاه ليست مرشحة لنقل منفرد بناءً على الأدلة الحالية.

## بوابات إلزامية قبل أول نقل

1. تشغيل `node scripts/validate-static-project.mjs`.
2. تشغيل `node --check` على جميع ملفات `.js` و`.mjs`.
3. تشغيل `python3 validate_project.py` دون تعديل بيانات قانونية تلقائيًا خارج سلوك الإصلاح الحالي المعتمد.
4. بناء `dist` بواسطة `scripts/build-pages-bundle.sh` وفحص الملفات والمسارات الناتجة.
5. اختبار أقسام الكتب، الاختبارات، البحث، القوانين، العرائض، منبر ميزان، لوحة الإدارة، وروابط المقالات على بيئتي النشر ذات الصلة.
6. مراجعة أي اختلافات في الملفات الناتجة قبل النشر.

## حدود التحقق

لم يتم تشغيل الأوامر أعلاه في بيئة محلية خلال هذه الخطوة، ولم تُختبر جلسات Firebase أو وظائف Vercel فعليًا. تم توثيق الاستنتاجات من ملفات المستودع فقط. لا ينبغي اعتبار هذه المذكرة شهادة نجاح اختبار أو تصريحًا بنقل ملفات التشغيل.
