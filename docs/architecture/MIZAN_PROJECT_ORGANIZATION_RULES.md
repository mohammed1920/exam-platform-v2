# ضوابط تنظيم مشروع منصة ميزان

> هذه الوثيقة هي المرجع المعتمد لتنظيم ملفات مستودع منصة ميزان. هدفها تنظيم المشروع تدريجيًا حسب المسؤولية، مع الحفاظ على سلوك الموقع وبياناته وأمانه واستقرار النشر.

## 1. نطاق التطبيق والفرع

- المستودع: `mohammed1920/exam-platform-v2`.
- الفرع المعتمد للعمل وفق سياسة المشروع الحالية: `main`.
- لا تُنشأ فروع جديدة ضمن هذه الخطة إلا إذا طلب مالك المشروع ذلك صراحةً.
- هذه الوثيقة تحدد البنية المستهدفة وضوابط التنفيذ؛ وجود مسار في الشجرة المقترحة لا يعني أن الملفات نُقلت إليه بالفعل.
- لا يُعاد بناء المشروع من الصفر، ولا تُحذف ميزة قائمة لمجرد تسهيل التنظيم.

## 2. الأهداف المعمارية

- جمع ملفات كل ميزة ومواردها في مكان واضح حسب مسؤوليتها.
- فصل منطق التطبيق المشترك عن ميزات المنصة وخدماتها وبياناتها وأدوات التطوير.
- تقليل التكرار والملفات المتضاربة، وعدم إنشاء بدائل لوظائف موجودة أصلًا.
- تسهيل الصيانة والاختبار والتطوير المستقبلي دون التأثير على الأقسام الأخرى.
- الحفاظ على الأداء، والتحميل الانتقائي للبيانات، وتوافق الهاتف واللوحي والحاسوب والوضعين الفاتح والداكن.

## 3. البنية المستهدفة

## 4. مسؤولية المجلدات

- `src/core/`: التهيئة العامة وتدفق التطبيق والتنقل المشترك، وليس منطق قسم متخصص.
- `src/design-system/`: المصدر المركزي للألوان والرموز والثيمات. لا تُضاف ألوان مستقلة متعارضة داخل الأقسام.
- `src/shared/`: وظائف وواجهات مشتركة فعلًا بين أقسام متعددة.
- `src/features/<feature>/`: منطق القسم وملفات CSS/JS الخاصة به. لا تُنقل ميزة إلى هنا قبل حصر جميع مراجعها.
- `src/services/`: تكاملات وخدمات مشتركة مثل Firebase وتحميل البيانات والبحث.
- `data/`: البيانات والمحتوى والفهارس. تُحفظ معرّفات السجلات وبنية البيانات المتوافقة مع التطبيق.
- `assets/`: الصور والشعارات والخطوط والموارد الثابتة، مع الحفاظ على مساراتها أو تحديث جميع المراجع.
- `api/`: نقاط النهاية التي يعتمد عليها نشر Vercel؛ يجب إبقاء المسارات المتوقعة متوافقة.
- `admin/`: ملفات واجهات الإدارة بعد التأكد من مراجع HTML والتحميل.
- `scripts/`: أدوات البناء والتحقق وتوليد الفهارس والصيانة.
- `tests/`: اختبارات آلية قابلة للتكرار. لا يُدّعى تنفيذ اختبار لم يُشغّل فعليًا.
- `docs/`: التوثيق وخريطة الاعتماديات وخطط التغيير.
- `.github/workflows/`: سير عمل GitHub Actions، ولا يُنقل خارج المسار الذي يتعرف عليه GitHub.

## 5. ملفات ومسارات يجب إبقاؤها في أماكنها حاليًا

إلى أن يُثبت فحص البناء والمراجع خلاف ذلك، تبقى الملفات التالية في الجذر أو مساراتها الحالية:

- `index.html` و`admin.html` لأن روابط وموارد الواجهة قد تعتمد على المسارات الحالية.
- `vercel.json` و`api/` لأن إعدادات التوجيه وواجهات Vercel تعتمد عليها.
- `manifest.json` و`robots.txt` وملفات التحقق من النطاق وملفات قواعد الأمان.
- `.github/workflows/` لأن GitHub يتوقع ملفات سير العمل داخل هذا المسار.
- `data/` ومجلدات الأسئلة الحالية إلى أن تُحدّث جميع مراجع التحميل والفهارس وسكربتات البناء.
- ملفات الأيقونات والموارد التي لم تُحصر مراجعها بالكامل.

## 6. ضوابط إلزامية قبل أي نقل

1. افحص جميع المراجع للملف: HTML وJavaScript وCSS وJSON وملفات البناء والإعدادات وسير العمل.
2. حدّد المراجع الثابتة والديناميكية، بما فيها المسارات المركبة وروابط التحميل والتحميل الكسول وService Worker.
3. انقل مجموعة صغيرة مترابطة في كل تغيير؛ لا تنفّذ نقلًا شاملًا دفعة واحدة.
4. حدّث المراجع في التغيير نفسه الذي ينقل الملفات.
5. لا تنشئ طبقات CSS إضافية أو أكواد التفافية أو محمّلات بديلة لمجرد تجاوز مشكلة في التنظيم.
6. لا تحذف ملفات يُشتبه بأنها غير مستخدمة قبل إثبات عدم وجود مراجع مباشرة أو ديناميكية إليها.
7. لا تغيّر أسماء الملفات أو معرّفات الأسئلة والقوانين أو شكل البيانات العامة دون حاجة موثقة وخطة توافق.
8. لا تغيّر قواعد Firebase أو المصادقة أو الصلاحيات بما يضعف الأمان.
9. لا تحمّل جميع الكتب أو الأسئلة إلى الذاكرة دفعة واحدة؛ حافظ على التحميل الانتقائي.
10. لا تغيّر تصميم أيقونات الكتب ثلاثية الأبعاد أو الهوية البصرية ضمن مهمة نقل الملفات.
11. حافظ على دعم RTL واللغة العربية، والأجهزة المختلفة، والثيمين الفاتح والداكن.
12. لا تضع أسرارًا أو مفاتيح خاصة أو بيانات مستخدمين في المستودع.

## 7. النشر والبناء

- افحص `scripts/build-pages-bundle.sh` قبل وبعد أي نقل، لأنه يحدد الملفات التي تدخل حزمة GitHub Pages.
- افحص `vercel.json` وإعدادات التوجيه وواجهات `api/` بعد كل تغيير ذي صلة.
- حافظ على سلوك روابط المقالات المباشرة وSEO و`sitemap.xml` و`robots.txt`.
- افحص `service-worker.js` والتخزين المؤقت وتحديث النسخة المنشورة؛ لا تحذفه ولا تغيّر مساره دون اختبار.
- افحص `manifest.json` وأيقوناته و`start_url` بعد تغيير أي مسار.
- يجب أن تكون الروابط المحلية صحيحة في بيئة الجذر والنشر والمعاينة، لا في بيئة التطوير فقط.

## 8. خطة التنفيذ المعتمدة

### المرحلة 1 — التوثيق والجرد
- تحديث خريطة الملفات والاعتماديات.
- توثيق الملفات الحساسة ومسارات التحميل والبناء والنشر.
- لا نقل لملفات التشغيل في هذه المرحلة.

### المرحلة 2 — الموارد والتوثيق والأدوات
- تنظيم الأصول والتوثيق وأدوات الفحص التي ثبتت مراجعها.
- تحديث كل المراجع ذات الصلة والتحقق من سلامتها.

### المرحلة 3 — وحدات الميزات
- نقل كل قسم مع ملفاته المرتبطة في تغييرات صغيرة: الكتب والاختبارات، القوانين، الإجراءات، العرائض، دليل المحامين، منبر ميزان، وحسابات الطلاب.
- بعد كل وحدة، تحقق من تحميل القسم وسلوكه قبل الانتقال إلى التالي.

### المرحلة 4 — الخدمات والبيانات
- فصل الخدمات المشتركة بعد تحديد الاعتماديات.
- تنظيم البيانات تدريجيًا فقط إذا كان ذلك يحقق فائدة فعلية، مع الحفاظ على معرّفاتها وعقودها ومسارات التحميل.

### المرحلة 5 — التحقق والإطلاق
- تشغيل فحوصات سلامة JSON والمراجع المحلية وCSS design tokens.
- اختبار الواجهة الرئيسية ولوحة الإدارة وتسجيل الدخول والبحث والاختبارات والأقسام القانونية والمقالات والعرائض.
- اختبار الوضعين الفاتح والداكن وعلى الهاتف والحاسوب.
- اختبار بناء GitHub Pages ونشر Vercel والروابط المباشرة وملفات SEO وPWA.
- مراجعة نتيجة كل اختبار وتوثيق أي فشل بدل الادعاء بالنجاح.

## 9. قائمة تحقق لكل تغيير

- [ ] حُددت الملفات والمراجع المتأثرة قبل التغيير.
- [ ] لا توجد ملفات مكررة أُنشئت بلا ضرورة.
- [ ] حُدّثت جميع المسارات ذات الصلة.
- [ ] لم تتغير البيانات أو المعرّفات أو الصلاحيات دون مبرر.
- [ ] اجتازت الملفات المنقولة فحوصات المراجع وJSON عند انطباقها.
- [ ] اختُبر القسم المتأثر يدويًا أو آليًا، وسُجلت الاختبارات التي لم تُنفّذ.
- [ ] لم يتعطل بناء GitHub Pages أو Vercel.
- [ ] وُثّق التغيير وأي مخاطر متبقية.

## 10. قاعدة القرار

عند التعارض بين ترتيب الملفات واستقرار المنصة، تُقدَّم سلامة التشغيل والأمان والبيانات على النقل. لا يُعتبر التنظيم مكتملًا لمجرد إنشاء المجلدات؛ يكتمل فقط بعد تحديث المراجع، واجتياز الفحوصات، والتحقق من عمل القسم والنشر.

## 11. ملاحظة الحالة

هذه الوثيقة تحدد الضوابط والبنية المستهدفة. لا تعني أن إعادة التنظيم قد نُفذت. يجب توثيق كل مرحلة لاحقة بملخص للملفات التي تغيّرت، والفحوصات المنفذة ونتائجها، وأي خطوات متبقية.
